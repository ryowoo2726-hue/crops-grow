# 학교망 신규 등록 최적화·검증 — 2026-11-13

신규 등록에서 자신이 방금 저장한 PIN 해시를 다시 계산하던 부분을 제거했다. scrypt의 비용·salt·키 길이는 유지한다. 다른 요청이 같은 번호를 먼저 등록했다면 그 학생의 salt로 다시 검증하며, PIN 변경·삭제 확인과 5회 실패 잠금도 유지한다. 학생의 공식 기록과 정답은 계속 SQLite 기준이다.

## 측정 환경과 범위

사용자가 학교 인터넷에 연결했다고 확인한 현재 노트북에서 측정했다. Core 5 120U / 논리 CPU 12개 / RAM 약 16GiB / Node 24.20.0, 유선 링크 100Mbps였다. 여유 RAM은 첫 측정 약 1.9GiB로 다른 작업이 있는 환경이다. 모든 등록·물 주기·로그인 부하는 별도 임시 DB와 별도 API를 사용했다. 운영 DB와 실행 중인 서버·Tunnel·DNS 설정은 변경하지 않았다.

## 수정 전후 비교

Git HEAD의 기존 백엔드를 OS 임시 폴더에 복사하고 수정본과 번갈아 3회 측정했다. 매번 새 프로세스·새 DB에서 100명을 동시에 등록했으며 작업 스레드는 양쪽 모두 4개다. 아래는 각 회차에서 가장 늦게 받은 응답이다.

| 조건 | 1회 | 2회 | 3회 | 실패 | 100명당 scrypt |
|---|---:|---:|---:|---:|---:|
| 수정 전 | 3.427초 | 2.602초 | 3.665초 | 0/300 | 200회 |
| 수정 후 | 1.416초 | 2.456초 | 1.322초 | 0/300 | 100회 |

회차별 최장 응답의 중앙값은 3.427 → 1.416초(약 59% 감소)다. 이는 모든 요청의 중앙값이 아니다. 다른 프로그램·발열·스케줄링을 통제하지 못했으므로 고정된 개선율을 보장하지 않는다. 확실하게 확인한 변화는 중복 암호 계산의 제거다.

수정 후 30명씩 3회 등록은 최장 0.466/0.487/0.431초, 실패 0/90이었다. 스레드 8개 단일 시험은 최장 1.481초·RSS 178.1MiB였고, 4개의 RSS 약 118~119MiB보다 메모리를 더 썼다. 반복 비교에서 일관된 이득을 확인하지 못해 운영 스레드 설정은 유지했다.

## 실제 학교 인터넷 경유

운영 게임 주소의 읽기 전용 health를 100건씩 3회 확인했다. 모두 HTTP 200·ICN, 실패 0/300, p95 321/106/103ms였다. 관리형 운영 Tunnel은 healthy·연결 4개였다.

격리된 임시 API에 Quick Tunnel을 연결했다. HTTP/2 시도는 health 확인에 실패했고 QUIC 시도는 연결됐다. 이 결과만으로 학교망의 TCP 차단 원인을 확정할 수는 없다. QUIC 터널에서 각각 100명씩 3회 수행한 결과는 다음과 같다.

| 작업 | 회차별 최장 응답 | 실패 |
|---|---|---:|
| 신규 등록 | 7.341 / 2.535 / 2.457초 | 0/300 |
| 물 주기 | 0.384 / 0.418 / 0.449초 | 0/300 |
| 기존 학생 로그인 | 2.568 / 2.658 / 9.760초 | 0/300 |

학교 회선을 통한 실제 HTTP 요청이지만 한 PC에서 발생시킨 부하다. 학생 단말 100대나 교실 Wi-Fi 무선 구간의 성능을 검증한 것은 아니다. 임시 터널은 운영 Pages 프록시 경로와도 다르다. 최초 QUIC 실행의 보고서 transport 문자열은 옵션 추가 전 실행되어 `quick-tunnel-http2`로 남았으나, 실제 실행 인수와 report.tunnel.protocol은 quic이다. 스크립트의 표시는 수정했다.

## 남은 지연과 운영 판단

초기 기존 코드의 로컬 100명 등록은 1회차 최장 9.524초, 2회차 30명 시간 초과, 3회차 최장 11.352초였다. 수정본도 별도 연속 부하 시험의 로컬 100명 등록 한 회차에서 13명이 12초 제한에 걸렸다. 같은 시험의 로컬 기존 로그인에도 총 38건의 시간 초과가 있었다. 해당 시험 전체는 실패로 종료됐으며 인터넷 구간 900건은 모두 성공했다. 시간 초과 뒤 서버 계산이 계속되어 다음 단계 계측에 섞인 경우도 있으므로 그 실행의 hashCalls를 독립 회차의 정확한 호출 수로 해석하지 않는다.

따라서 최적화 후에도 이 PC에서 100명 동시 신규 등록의 안정성을 보장할 수 없다. 운영 시 30명 정도씩 나누는 방식을 권한다. 순간 지연 원인은 아직 확정하지 않았으며 암호 강도를 낮추거나 요청 제한만 늘려 해결했다고 처리하지 않았다.

현재 사용자가 켜 둔 API와 Tunnel은 그대로 가동 중이다. **실행 중 프로세스에는 코드가 자동 반영되지 않으며 다음 서버 재시작부터 최적화를 사용한다.** 새 DB 형식 변경이나 학생 기록 변환은 필요 없다. 임시 API·터널·DB는 모두 정리했다. 원시 성능 JSON은 OS 임시 폴더에만 저장한다.

# 이전 신규 등록·추가 지연 검증 — 2026-11-12

**이 노트북의 신규 등록 100명 동시 처리는 반복 시험에서 성공했다. 인터넷이 심하게 지연되면 앱의 12초 제한으로 로그인에 실패할 수 있다.** 이전에 관찰된 11.432초 등록 지연은 재현되지 않았으며 원인을 확정하지 않았다.

## 지연이 발생하는 부분

테스트 프로세스에서 비밀번호 해시 호출과 SQLite 작업 시간을 계측했다. 제품 코드의 해시 방식이나 운영 설정은 변경하지 않았다.

- 신규 등록 100명에는 scrypt 호출이 **200회** 발생했다. 현재 구현은 새 비밀번호 해시 생성 후 인증 검증도 수행한다.
- 대기·계산을 합친 해시 호출의 95% 완료 시간은 1.219~1.390초였고, 동시에 대기 또는 계산 중인 호출은 최대 100개였다. 이 수치는 실제 CPU 작업 스레드 100개를 뜻하지 않는다.
- SQL 준비·실행의 누적 시간은 100명 회차당 약 0.588~0.638초였다. 동시 작업 시간이 중첩되는 해시 대기 시간과 단순 합산할 수 없다.
- 서버 프로세스 평균 CPU 사용은 12개 논리 CPU 전체를 100%로 환산해 약 32.6~33.3%, 최고 RSS 샘플은 약 125~128MiB였다.

측정상 물 주기보다 신규 등록의 암호 처리·대기가 훨씬 큰 지연 요인이다. 최초 11.432초 지연까지 이 요인만으로 설명할 수 있는지는 확인하지 못했다.

## 인터넷 지연을 가정한 첫 로그인

로컬 HTTP 프록시에서 요청 전달 전과 응답 전달 전에 각각 지연의 절반을 추가했다. 표의 ‘추가 왕복 지연’은 **HTTP 요청 한 번당** 추가한 RTT다. 첫 로그인은 브라우저와 같이 **OPTIONS 사전 확인 + POST 등록**을 순서대로 수행하고 두 요청 전체에 앱과 같은 12초 제한을 적용했다. 성공한 사전 확인은 재시도 때 캐시된 것으로 처리했다.

**실제 학교 Wi-Fi나 운영 Cloudflare Tunnel에서 측정한 값이 아닌 인위적 지연 시험이다.** 대역폭 제한·패킷 손실·TLS 연결 지연은 별도로 재현하지 않았다. 각 지연 조건은 1회이며 시점별 CPU 부하와 요청 스케줄링이 달라 전체 시간이 추가 지연과 정확히 비례하지는 않는다.

시간 초과는 화면이 응답을 받지 못한 것이며, 서버에서는 이미 등록됐을 수 있다. 재시도에서 같은 학년·반·번호와 같은 PIN을 사용했고 **최종 학생 수는 각각 100명 또는 30명으로 중복 생성되지 않았다.** 10초 RTT 조건은 등록 행이 생성된 후에도 로그인 응답을 제한 시간 안에 받지 못했다. 이런 연결에서는 재시도만으로 정상 플레이를 보장할 수 없다.

## 암호 작업 스레드 8개 실험

별도 테스트 자식 프로세스에만 `UV_THREADPOOL_SIZE=8`을 적용해 100명 등록을 3회 시험했다. 최장 응답은 **1.603~2.052초**, 실패 0/300이었다. 서버 최고 RSS 샘플은 약 **191MiB**, 서버 평균 CPU 사용은 전체 논리 CPU 기준 약 **60~63%**였다. 현재 설정보다 빨랐지만 CPU/RAM을 더 사용했다. **운영 설정은 바꾸지 않았다.**

## 530·429와 운영 판단

- 재확인 당시 로컬 `127.0.0.1:8787` API에는 연결되지 않았고 외부 `/api/health`는 **530**이었다. 이 상태에서는 공식 로그인·물 주기 저장·수확이 불가능하다. 게임 웹 파일의 정상 배포와 API의 가동은 별개다.
- **429는 별도 Quick Tunnel 생성 단계에서 발생**했다. 이번 시험에서 학생 플레이 API가 429를 반환한 것은 아니다. 운영 Tunnel/DNS 설정은 변경하지 않았다.
- 운영 전에 API와 Tunnel을 실행하고 외부 `/api/health`가 **200**인 것을 먼저 확인해야 한다. 이후 실제 학교 Wi-Fi에서 첫 로그인과 물 주기를 확인해야 인터넷을 포함한 지연을 판단할 수 있다.
- 최초 등록은 30명 정도씩 나누면 로컬 서버 대기가 줄어든다. 심한 인터넷 지연은 인원을 줄이는 것만으로 해결되지 않는다는 결과도 확인했다.

## 재현과 정리

`node tests/registration.load.cjs`는 인원별 등록·POST 지연·작업 스레드·60초 유휴 후 등록·사전 확인을 포함한 지연 시험을 실행한다. `--preflight-only --delay-ms=2000 --count=100`으로 특정 조건만 실행할 수 있다. 토큰·PIN은 출력/보고서에 저장하지 않고 각 임시 DB와 API를 종료/삭제한다. 원시 성능 JSON은 OS 임시 폴더에만 보관한다. 이 보고서에는 실제 학생 정보와 비밀번호가 없다.
