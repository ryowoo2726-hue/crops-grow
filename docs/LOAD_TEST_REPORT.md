# 100명 동시 접속 검증 — 2026-11-12

이 노트북의 **100명 동시 물 주기 처리는 통과**했다. 메모리 부족이나 서버 종료, 기록 오류는 관찰되지 않았다. 실제 학교 Wi-Fi와 학생 기기 100대를 통한 인터넷 접속은 아직 검증하지 않았다.

## 측정 환경과 방법

- CPU: Intel Core 5 120U, 물리 10코어·논리 12스레드.
- RAM: OS에서 사용 가능한 총 16,067MiB(약 15.7GiB). 추가 측정 시작 여유 2,601MiB, 측정 중 최저 여유 2,457MiB.
- Node.js v24.20.0, 현재 백엔드 코드, 노트북 로컬 임시 SQLite.
- 실제 API를 별도 Node 프로세스에서 실행하고 각 단계에 HTTP 요청 100개를 동시에 보냈다. 순서는 신규 등록 → 물 주기 → 기존 학생 로그인이다. 3회 반복하며 매 회 새 가상 학생 100명을 사용했다.
- 기본 데이터로 900건, 퀴즈 20문제·특별 미션·학생별 수확 3개를 포함한 추가 측정으로 900건, **총 1,800건 중 실패 0건**이다. 이 중 물 주기는 총 600건이다. 미션/수확 데이터 추가는 측정 단계 밖에서 수행했다.
- 공식 DB·학생·관리자 비밀번호·운영 Tunnel/DNS는 변경하지 않았다. 테스트 토큰과 가상 학생 DB는 측정 뒤 삭제했다. 원시 성능 JSON은 OS 임시 폴더에만 보관한다.

## CPU와 RAM

- 백엔드 프로세스 최고 메모리: **131.1MiB**(Windows의 PeakWorkingSet64 137,416,704바이트). 물 주기 단계의 최고 RSS는 58~67MiB, 로그인 단계는 118~131MiB였다.
- 백엔드의 JavaScript 힙 사용량은 약 8~13MiB였다. 현재 환경에서 읽은 힙 상한은 4,288MiB이며, 이 크기를 처음부터 RAM에 확보하는 설정은 아니다. 별도 RAM 할당 설정은 변경하지 않았다.
- 12개 논리 CPU 전체 용량을 100%로 환산한 서버 프로세스의 단계 평균 사용량은 물 주기 **4.3~5.7%**, 신규 등록/로그인 **31.2~33.2%**였다. 운영체제 전체 CPU 사용률이 아니라 서버 프로세스 사용량이며, 서로 다른 성능의 코어를 같은 비중으로 환산한 근삿값이다.
- 동시 물 주기 단계의 이벤트 루프 최대 지연은 약 130~185ms였다. SQLite 쓰기는 순차 처리되지만 100건 모두 정상 완료됐다.
- 서버 메모리는 현재 남아 있는 RAM에 비해 작다. 행사 때는 다른 무거운 앱과 불필요한 브라우저 탭을 줄이고 **최소 1GiB 이상 여유 RAM**을 확보하는 운영을 권한다. 이 수치는 측정된 약 131MiB 서버 사용량에 여유를 둔 운영 기준이며 RAM 사용 제한을 새로 설정한 것은 아니다.

## 인터넷 측정과 한계

- 현재 연결은 Realtek 유선 어댑터 **100Mbps 링크**다. Wi-Fi는 연결되지 않았다. 100Mbps는 랜카드 링크 표시이며 인터넷 업로드 실측 속도는 아니다.
- 실제 프론트 도메인의 작은 `version.json`을 7번 조회했다. 첫 응답 TTFB는 594ms, 이후 6회는 **23~54ms, 중앙값 약 45ms**였다. 이는 Cloudflare의 프론트 파일 응답이며 노트북의 게임 API 응답 시간이 아니다.
- 운영 API `/api/health`는 측정 시 HTTP **530**이었다. 운영 서버·Tunnel을 켜거나 해당 설정을 변경하지 않았다.
- 운영 도메인과 분리한 HTTP/2 Quick Tunnel로 인터넷 경유 시험을 시도했지만 **임시 Tunnel 생성 단계에서 Cloudflare 429**가 반환됐다. 게임 요청 100건 때문에 발생한 429가 아니다. 임시 연결이 성립하지 않아 인터넷 경유 100명 부하는 검증하지 못했다. 시도한 임시 프로세스는 종료했다.
- 이 보고서의 부하 응답 시간에는 학생 Wi-Fi, 학교 인터넷, Cloudflare Tunnel 왕복 시간이 포함되지 않는다. 장시간 운영·절전/발열·학생 기기 렌더링 성능도 이번 짧은 부하 시험 범위에 포함되지 않는다.

## 재현

`node tests/backend.load.cjs`는 새 임시 DB·별도 API로 100명씩 3회 시험하고 원시 JSON을 OS 임시 폴더에 저장한다. 종료 후 테스트 DB를 삭제한다. `--tunnel`을 추가하면 별도 Quick Tunnel 연결도 시도한다. 운영 서버나 학생 데이터를 사용하지 않는다.

실제 행사 전에는 운영 API와 Tunnel을 정상 실행한 뒤 학교 Wi-Fi의 학생 기기에서 로그인·물 주기를 확인해야 인터넷을 포함한 최종 지연을 판단할 수 있다.
