# 운영 인터넷 연결·로딩 진단 — 2026-11-12

사용자가 서버 연결을 완료한 뒤 실제 도메인을 측정했다. **외부 API 200은 확인했지만 접속 경로의 지연·시간 초과·502도 발생해 아직 100명 접속이 안정적이라고 판단하기 어렵다.** 공식 학생 등록·물 주기·수확은 실행하지 않고 health 조회, 관리자 목록 읽기, 공개 로그인 화면으로 측정했다.

## 1. API 서버 자체와 인터넷 구간

| 항목 | 결과 |
|---|---|
| 로컬 health 반복 조회 | 첫 요청 약 70ms, 이후 대부분 3~16ms |
| 로컬 health 100개 동시 조회 | 중앙값 90ms, 95% 103ms, 최장 105ms, 실패 0 |
| 외부 health 반복 조회 | 연결 재사용 시 약 0.50~0.58초, 초기 연결/일부 요청은 약 1.7~5.8초 |
| 관리자 목록 읽기 | 로컬 2~16ms, 외부 0.486~1.812초 |
| 프론트 version.json 반복 조회 | 약 22~79ms |

관리자 세션은 로컬에서 만들고 동일한 토큰으로 외부 목록 읽기에 성공한 뒤 로그아웃했다. 외부 API가 이 로컬 API 프로세스에 연결된 것을 확인한 것이며, 학생 개인정보·비밀번호·토큰은 보고서에 저장하지 않았다. 측정 당시 학생 목록은 비어 있었다.

인터넷 경유 health 100개 동시 조회를 3회 실행했다. 이 요청은 DB를 읽거나 게임 기록을 바꾸지 않는다. 단일 노트북에서 낸 HTTP 부하이며 학생 기기 100대의 실제 수업 시험과는 구분한다.

| 회차 | 중앙값 | 95% 응답 | 최장 | 실패 |
|---|---:|---:|---:|---:|
| 1 | 2.019초 | 5.005초 | 10.195초 | 1/100 |
| 2 | 1.097초 | 2.326초 | 4.949초 | 0/100 |
| 3 | 10.369초 | 11.620초 | 약 12초 제한 | 4/100 |

총 **300건 중 5건 실패**: 연결 오류 TypeError 1건, 12초 시간 초과 4건. 다른 단일 진단 요청에서도 시간 초과가 있었다. 실제 학생 신규 등록의 암호 계산과 게임 동작을 더하지 않은 조건에서도 발생한 지연이다.

## 2. API 접속 경로 차이

기본 API 요청은 응답 `Cf-Ray` 끝에 **LAX**, 프론트 파일은 **ICN**이 표시됐다. Chrome에서도 API 요청이 **HTTP/2·LAX**로 처리되는 것을 확인했으므로 Node 테스트만의 현상은 아니었다. Cf-Ray의 데이터센터 표식 해석은 [Cloudflare 공식 설명](https://developers.cloudflare.com/fundamentals/reference/http-headers/)을 따른다. 이 코드 하나만으로 모든 내부 경로를 확정하는 것은 아니다.

같은 API URL·TLS 인증서 검증을 유지하고 curl 진단 요청의 접속 IP만 일시 지정해 비교했다.

| 진단 경로 | 관찰 결과 |
|---|---|
| API DNS가 반환한 IP의 기본 경로 | LAX, 정상 응답도 약 0.99~7.92초로 변동. 후속 4회 중 2회 502 |
| 다른 Cloudflare 접속 IP를 지정한 비교 경로 | ICN, 4회 모두 실제 `{"ok":true}` 검증, 약 77~115ms |

비교 경로의 앞선 최초 시도에서도 TCP 연결에 7초가 걸린 사례가 있으므로 ICN 경로가 항상 빠르다고 보장할 수는 없다. 다만 같은 서버의 정상 응답이 0.1초 안팎에 도착할 수 있다는 점과 기본 접속 경로의 큰 차이는 확인했다. 이 실험은 요청별 `--resolve` 지정이며 시스템 DNS·hosts·Cloudflare DNS를 변경하지 않았다. 특정 Cloudflare IP를 운영 설정에 영구 고정하는 방안은 권하지 않는다.

터널 지표에서는 주 프로세스가 ICN 계열 연결 4개를 유지했고 origin 프록시 오류 카운터는 0이었다. 프로세스 2개가 보였지만 두 번째는 요청 처리 0건이었고 연결 수가 4에서 0으로 변했다. 중복 프로세스가 지연의 원인이라고 확정하지 않았고 사용자의 프로세스를 종료하지 않았다.

## 3. DNS에서만 6.1초 걸린 첫 접속

추가 Chrome 측정에서 첫 화면이 **7.566초**에 떴다. 이때 Navigation Timing의 DNS 구간이 **6.100초**, HTML 첫 바이트가 6.159초였다. 같은 회차의 재접속은 DNS 0ms, HTML 첫 바이트 약 23ms, Flutter 첫 화면 **0.658초**였다. 이 회차 첫 화면 대기의 약 81%가 DNS 구간이었다.

간헐적인 DNS 지연은 확인했으나 학교 DNS, 보안 DNS, 회선 또는 브라우저 중 어느 부분이 원인인지는 아직 분리하지 못했다.

## 4. 화면 파일과 로그인 자료 선준비

390×844 Chrome의 실제 회선·무제한 조건으로 3회씩 측정한 첫 화면은 **1.797/4.165/1.579초**, 재접속은 **2.914/4.183/6.422초**였다. 추가 추적은 첫 접속 1.549초·재접속 0.981초, 경로 확인 측정은 첫 접속 7.566초·재접속 0.658초였다. 일부 회차 차이가 커서 한 번의 최선값을 일반적인 속도로 보지 않는다.

별도 **8Mbps·40ms 제한** 조건 3회는 첫 화면 5.837/11.456/12.032초였다. 이는 실제 회선 무제한 측정과 구분한다. 느린 회선에서 엔진·폰트 전송이 크게 영향을 주는 것을 확인했다.

첫 접속 때 전체 후속 준비까지 전송한 리소스 합계는 약 **7.30MB**였다. 주요 초기 파일은 다음과 같다.

| 파일 | 전송 크기 |
|---|---:|
| 한글 코어 폰트 | 약 1.63MB |
| Skwasm 엔진 | 압축 약 1.54MB |
| 게임 Wasm 코드 | 압축 약 0.84MB |
| 후속 한자 보조 폰트 | 약 2.32MB |

완전히 준비한 뒤 재접속하면 해시가 있는 코드·엔진·폰트·이미지의 추가 전송은 0바이트였다. 약 7KB의 작은 파일 요청만 남았다. 캐시 재사용은 정상이다. 추가 추적의 캐시 재접속에서도 약 609ms 긴 메인 스레드 작업이 관찰되어 다운로드를 생략해도 Flutter 초기화 비용은 남는다.

특히 `preparePlay()`는 `galleryPreparation`을 기다리고, 이 Future 안에는 보조 폰트 `FontLoader.load()`까지 포함된다. **보조 한자 폰트가 로그인 입장 완료 조건에 포함된 상태다.** 실제 추적 한 회차에서 이 폰트 요청은 시작 2.637초, 완료 10.082초로 **7.445초** 걸렸다. 로그인 API가 먼저 끝나도 이 준비가 끝나지 않았다면 입장이 추가 지연되는 구조다. 실제 학생 로그인을 실행하지 않았으므로 그 학생의 전체 로그인 소요 시간으로 보고하지는 않는다.

## 5. 불필요한 사전 확인 요청

`BackendClient.call()`은 본문 없는 GET에도 `Content-Type: application/json`을 붙인다. Chrome에서 첫 `/api/health`에 실제로 **OPTIONS 204 → GET 200**이 발생했다. 추가 warm 측정에서 사전 확인은 TLS 연결을 포함해 약 1.688초, 뒤의 GET은 약 0.756초였고 전체 health 요청이 약 2.460초 걸렸다.

인증도 JSON 본문도 없는 health GET에서 이 헤더를 생략하면 사전 확인 왕복 한 번을 줄일 수 있다. 수정 후 효과를 측정한 것은 아니므로 절약 시간을 확정하지 않는다. 인증 헤더가 필요한 다른 조회나 JSON POST는 별도 판단이 필요하다.

## 개선 우선순위

1. **API 접속 경로와 간헐적 DNS 지연**을 먼저 점검한다. 로컬 처리보다 외부 연결 구간이 훨씬 느리고 502·시간 초과도 관찰됐다.
2. **필수 이미지 준비와 한자 보조 폰트 준비를 분리**한다. 미리 불러오기는 유지하되 보조 폰트가 게임 입장을 막지 않게 하는 것이 확인된 코드 개선 지점이다.
3. **본문 없는 health GET의 불필요한 JSON 헤더를 제거**해 초기 사전 확인 왕복을 줄인다.
4. 초기 약 4MB의 엔진·코어 폰트·앱 전송을 더 줄일 수 있는지 검토한다. 글자 지원을 보존하면서 초기 UI용 폰트를 더 나누는 방안은 별도 구현·검증이 필요하다.

이번 요청은 진단이므로 제품 코드와 운영 DNS·Tunnel 설정을 바꾸지 않았다. 측정 스크립트와 이 보고서만 갱신했다.

## 재현 및 한계

`node tests/internet.api.cjs`는 로컬/외부 health와 프론트 작은 파일 조회, health 동시 100건 시험을 수행한다. `--admin-read`는 비밀번호를 stdin으로 받고 읽기만 수행한 뒤 생성한 관리자 세션을 로그아웃한다. 비밀번호와 토큰은 출력하지 않는다.

로그인 화면은 `GROWGAME_TEST_URL=https://cropgrow.sangsangbar.com/`, `GROWGAME_TEST_PRODUCTION=true`, `GROWGAME_TEST_UNTHROTTLED=true`로 `node tests/loading.browser.cjs after-internet-natural`을 실행한다. 기본값은 기존처럼 8Mbps·40ms 제한이므로 조건을 구분해야 한다. `GROWGAME_TEST_TRACE=true`, `GROWGAME_TEST_ROUNDS=1`로 OS 임시 폴더에 Chrome 추적을 남길 수 있다.

실제 학생 로그인·물 주기·수확은 실행하지 않았다. 측정은 이 노트북의 회선에서 수행했고 다른 교실 Wi-Fi·학생 기기 100대의 성능으로 일반화하지 않는다. 게임이 Canvas 기반이므로 여기서는 Flutter 첫 프레임과 리소스·메인 스레드 시간을 사용했고 공식 현장 Core Web Vitals 등급은 산정하지 않았다. 원시 JSON·추적·스크린샷은 OS 임시 폴더에만 둔다.
